# Artemis 统一开发工作流

本文件适用于 Codex、Claude 及人工开发。风格只维护在 [STYLE.md](STYLE.md)，技术边界见 [PROJECT.md](PROJECT.md)，文档位置和模板见 [索引](README.md)。

## 1. 理解现状与分级

先读相关规范、代码和测试，检查工作区已有改动与进行中的变更。保留用户未提交的工作。识别本次目标、影响范围、不做的内容和验收方式；已有相同目标的变更记录应继续使用。

| 类型 | 记录要求 |
| --- | --- |
| 轻量：错字、局部样式、纯格式、恢复既有明确行为的小修 | 可直接修改；在交付说明或 PR 中记录目标、依据和验证结果 |
| 标准：新增能力、可观察行为变化、接口或数据结构变化、跨模块改造 | 实现前建立 `changes/<change-id>/change.md`，填写目标、需求增量、设计和任务 |
| 重点：鉴权、安全边界、数据库迁移、并发写入、同步/回滚、发布更新行为 | 使用标准记录，额外说明兼容性、失败路径、迁移/恢复方法及针对性验证 |

按实际影响分级，不按修改行数判断。恢复既有行为的小修若涉及重点领域，仍使用重点流程。轻量改动一旦扩大范围，应补建变更记录再继续。纯文档规则变更若影响后续开发方式，按标准流程记录；无需伪造业务代码测试。

## 2. 描述目标与验收

标准与重点变更使用 [变更模板](templates/change.md)，状态先记为 `draft`。至少写清：

- 为什么改，当前行为与预期行为，范围及不做的内容。
- 受影响能力和规范位置；需求用稳定 ID（例如 `TL-001`），每项至少一个可观察的验收场景。
- 增量标记 `ADDED`、`MODIFIED`、`REMOVED`；修改给出该需求的完整新语义，删除说明兼容或替代方式。
- 代码入口、技术方案、必要的取舍和风险；无设计复杂度时简述即可。
- 可逐项完成的任务，以及对应的测试、命令或人工检查。

新能力的预期行为先写在变更记录，不能提前当作已落地事实写入 `specs/`。既有能力缺少规范时，只为本次涉及的范围补齐有依据的基线。

需求明确且已获用户授权即可进入 `implementing`，不要求用户逐阶段确认。若用户只要求方案，完成方案即停在 `draft`，不得自行实现。关键语义、范围或破坏性操作缺少授权时明确询问，其他独立工作可以继续。

## 3. 实现并保持一致

按照任务清单修改，实际完成后才勾选。风格变更更新 STYLE.md；架构规则变更更新 PROJECT.md；入口文件保持相同引用。

实现中发现原方案不成立，先修订需求、设计与验收，再继续。记录影响决策的理由，不保留已废弃方案作为执行指令。同一能力有多个变更时检查重叠需求，避免归档时覆盖另一个变更的新规则。

受阻时记录阻塞原因、剩余任务和恢复条件，不把未执行的验证写成通过，也不因进度压力归档。

## 4. 按影响验证

验证命令应基于仓库实际脚本，不能假设存在 `npm test` 或 `npm run typecheck`。以下为选择依据，不要求每次全部执行：

| 改动范围 | 相关验证 |
| --- | --- |
| 仅文档 | 相对链接与路径、规则冲突、入口一致性、原约束保留情况、`git diff --check` |
| Go | 对改动文件执行 `gofmt`；相关包 `go test`、`go vet`，按依赖影响执行 `go build ./...` |
| 前端 | 在 `web` 下执行 `npx tsc --noEmit`、`npm run check -- <改动文件>`；相关现有测试与必要的静态构建 `npm run build:static` |
| UI 行为/样式 | 检查涉及页面的深浅主题、移动端、加载/空/错误状态与关键交互 |
| 数据、同步、快照、鉴权 | 针对性覆盖失败、并发、边界和恢复场景；数据库隔离要求见 PROJECT.md |
| 正式发布 | 使用 PROJECT.md 的正式构建方式，验证首次初始化、鉴权和空业务列表 |

Go 测试可能通过配置或环境读取数据库，运行前必须确认使用隔离测试 PostgreSQL；不能因为选择了单个测试就假定不会连接数据库。数据库缺失导致跳过的测试应单列，不能据退出码声称集成场景通过。

记录执行位置、实际命令、结果、未执行项及原因。补充能捕捉行为回归的测试；单纯排版或可逆低影响改动不强制新增测试。已有失败应与本次引入的问题区分，并说明影响。

## 5. 同步规范、归档与交付

验证完成后标记 `verified`，并依次执行：

1. 将需求增量合并进 `specs/<capability>/spec.md`：新增需求、替换被修改需求的完整内容、移除已废止需求；保留无关需求。现行规范不保留增量标记和任务清单。
2. 按需同步 STYLE.md、PROJECT.md、SPEC 能力索引及用户文档。记录实际更新位置；不涉及能力行为时说明理由。
3. 检查所有任务和必需验收均完成、文档与实现一致、没有未解决阻塞。未通过或必需项未执行时保持进行中并如实交付进度。
4. 将整个变更目录移入 `changes/archive/<YYYY-MM-DD>-<change-id>/`，修复因目录深度变化而失效的相对链接，再标记 `archived`。归档是文档动作，不意味着已提交、合并或发布。
5. 交付说明列出变更效果、关键文件、验证结果与剩余限制。提交、推送及发布遵循用户授权范围。

状态顺序为 `draft → implementing → verified → archived`。验证后若继续改动，退回 `implementing` 并重新执行受影响检查。取消的变更标记 `cancelled`，说明原因后可移入归档，不能合并为现行能力或声称已实现。
